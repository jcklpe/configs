# LifeOS Planner Labels and Comments
## Purpose and Scope
Extend the Planner CLI, now owned by `agent-hands/use-planner/` with legacy routing in `agent-hands/compat/lifeos/`, so approved task status changes do not require a browser. Implement existing-label listing, applying and removing labels with dry runs, allowlisted plans, existing authorization, concurrency checks, audit evidence and readback. Preserve unrelated working changes. No generic Graph command, credentials, OAuth scope expansion or browser fallback is authorized.
## API Findings
Microsoft documents `appliedCategories` in the [v1.0 task update API](https://learn.microsoft.com/en-us/graph/api/plannertask-update?view=graph-rest-1.0); the configured `Tasks.ReadWrite` permission supports labels. Resolve category IDs through plan `categoryDescriptions`, never guess from colors or create a label implicitly. A name must match exactly one existing label, case-insensitively. Merge current categories, guard the task ETag and compare active sets because the service can omit false values. Recheck label names before writing; their separate plan-details ETag cannot be atomically guarded with the task.

Planner comments are group conversation posts, not task details. [Listing posts](https://learn.microsoft.com/en-us/graph/api/conversationthread-list-posts?view=graph-rest-1.0) requires `Group-Conversation.Read.All` or a documented higher permission. [Replying](https://learn.microsoft.com/en-us/graph/api/conversationthread-reply?view=graph-rest-1.0) and [creating a thread](https://learn.microsoft.com/en-us/graph/api/group-post-threads?view=graph-rest-1.0) require delegated `Group.ReadWrite.All`. Initial inspection found that configured scopes omit these and a standalone `Get-MgContext` returned no active context. That was insufficient evidence of the effective transport permissions. The LifeOS auth command, using the unchanged configured scopes, subsequently confirmed existing effective `Group.Read.All` and `Group.ReadWrite.All`. No OAuth expansion or credentials were needed.

The explicitly requested extension therefore adds task-scoped list/add using existing effective permissions, checked at runtime through the graph-powershell auth metadata. Other providers and missing permissions fail closed. Group posts can generate ordinary group notifications; dry runs state this. The first comment needs a new group thread and an ETag-guarded task link. Do not claim completion before both are verified. Recovery journals record pending creation/reply/link states before writes; an unknown creation result is blocked for inspection, and known pending threads can be linked without reposting. Complete bounded thread reads and visible-text normalization prevent routine duplicates. A local task lock serializes CLI operations; the API cannot guarantee atomic deduplication against concurrent remote posts.
## Implementation and Validation
Label changes send a merged category map and no other task properties. Missing or ambiguous labels fail before writes; repeating the requested state is a no-op. Audit an attempt before transport, fail without retry after ambiguous outcomes, then verify the active label set and every unrelated task property except the ETag. Offline fixtures exercise the label PATCH, ETag, merge and failure paths. The live approved target already had its requested label when re-read, so both dry run and execute returned a no-op. Live listing and no-op behavior are verified; a real label PATCH remains unverified. Do not toggle an existing label merely to manufacture a live write test. Private execution evidence stays outside configs.

Comment list, first-thread creation, post readback, task linking and repeat no-op were validated live. The first immediate post read returned 404 after thread creation; the command retained its pending-link journal and stopped. A later read-only recovery found the exact post, and execution linked that existing thread without another POST. Independent readback confirmed a single post and preserved task fields. This establishes first-comment and known-thread recovery behavior; live existing-thread reply still has only offline coverage. The transient 404 was observed, but its service-side cause is not established.
