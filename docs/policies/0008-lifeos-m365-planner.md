# 0008 LifeOS Microsoft 365 Planner
## Current Approach
Use `bash agent-hands/use-planner/scripts/planner` (path relative to configs) as an opt-in surface per account alias, configured with a `planner` block in `m365-accounts.json`.

- **Reads:** `plans`, `buckets`, `tasks` (filters `--bucket`, `--mine`, `--open`), `task` (with description and checklist), and `labels` (existing named plan labels).
- **Scopes:** an alias with Planner enabled always requests `Tasks.ReadWrite`, plus `User.ReadBasic.All` so assignee IDs render as names. UT blocks user consent (the same wall `Files.ReadWrite` hit before admin consent on 2026-09-18), and `Tasks.ReadWrite` is already approved for the shared client while `Tasks.Read` is not, so requesting the narrower scope would stall on an admin-approval prompt. Write safety therefore lives in the CLI: `planner.write_enabled`, the plan allowlist, and dry-run-by-default.
- **Snapshot:** `export ALIAS --output PATH` writes the plans listed in `planner.plans` to an explicit caller-selected path, open tasks grouped by bucket and completed tasks in a compact list. Only configured plans are snapshotted, so the vault does not quietly grow to every plan the account can see.
- **Refresh selection:** callers select each account and output explicitly. Aggregate `lifeos sync` is retired; the old `planner.sync` flag no longer triggers or suppresses an aggregate refresh. Workspace policy decides which snapshots to refresh.
- **Writes:** `create-task` and `update-task` (title, bucket, due date, progress, assign and unassign, description). They run only when the alias sets `planner.write_enabled`. Writes are dry-run by default, need `--execute`, and are limited to plans in `planner.plans`. Each update sends `If-Match` with the etag read at the start of that run, so a task someone changed in between is refused rather than overwritten. Every executed write is read back and appended to the audit log (ignored `task-writes.jsonl` beside the owning Planner skill, service `m365-planner`).
- **Labels:** `label` and `unlabel` resolve an existing label by unique case-insensitive exact name, merge its requested state with current categories, and preserve unrelated fields. They use the same allowlist, write gate, dry-run default, ETag and audit boundary. Reapplying a state is a no-op. Attempts are audited before the PATCH; readback compares active categories and all other task properties except the ETag. Plan label names are rechecked before writing, but the separate plan and task resources cannot be guarded atomically. No label creation or renaming is exposed.
- **Comments:** `comments --task ID` and `comment --task ID --file PATH` expose only a known allowlisted task's group conversation, not arbitrary group posting. The graph-powershell provider must already have the documented effective permission: [post listing](https://learn.microsoft.com/en-us/graph/api/conversationthread-list-posts?view=graph-rest-1.0) accepts `Group-Conversation.Read.All` or a documented higher permission; [thread reply](https://learn.microsoft.com/en-us/graph/api/conversationthread-reply?view=graph-rest-1.0) and [thread creation](https://learn.microsoft.com/en-us/graph/api/group-post-threads?view=graph-rest-1.0) require delegated `Group.ReadWrite.All`. Scope inspection reconnects with the unchanged configured scope request and examines only auth metadata. It never adds permissions, creates credentials, uses private endpoints or browser sessions. Missing permissions stop the operation for approval. Existing effective group permissions were verified in the managed tenant on 2026-10-17 without scope expansion.
- **Comment writes:** same allowlist/write gate and dry-run default as task writes. Preview the exact file text and the possibility of Microsoft 365 group notifications. Read the full linked thread for text duplicates, bounded at 20 pages/1000 posts; reject partial reads. Compare whitespace-normalized visible text after HTML conversion. A first comment creates a group thread and conditionally links it through `conversationThreadId` using the original task ETag. Verify both the post and task link, plus unrelated task fields. Audit hashes and post/thread IDs rather than copying comment bodies into logs. A private per-task recovery journal and lock beside the audit log guard local retries. If creation has no known returned ID, stop for inspection; never blindly repeat. A known created thread can be linked after verifying its post, without reposting. An uncertain reply is retried only as a read: if the text is not visible, stop. Remote concurrent identical posts cannot be atomically deduplicated by the group API. Preserve journals/locks until outcomes are resolved.
- **No delete** is exposed.

## Rationale
Configured team plans need to be ordinary local context, with bounded task updates when authorized. The implementation targets basic Planner plans. In the managed tenant, the shared Graph PowerShell client has approved `Tasks.ReadWrite` while narrower `Tasks.Read` consent is unavailable; CLI opt-in, the plan allowlist, dry-run execution, and ETag guards therefore provide the write boundary.

## Operating Notes
- Refresh a configured plan through its explicit service export; the calling workspace owns its destination and freshness requirements.
- The plan is shared with the whole team, so any write is visible to them. The dry-run plan says so, and vault skills should treat Planner writes as outward-facing.
- The etag guard protects within one run; it cannot detect changes made between a dry run and a later `--execute`, which re-reads the task and shows its current state again.
- Enabling Planner adds `Tasks.ReadWrite` and `User.ReadBasic.All` to the requested scopes. Any change to the requested set needs one interactive `bash agent-hands/setup-microsoft-services/scripts/authorize auth ALIAS` (run in a real terminal; `--no-browser` uses a device code) before Planner calls work; until then they stall waiting for sign-in.

## Rationale for Limits
- **Requesting `Tasks.Read` for read-only aliases.** Tried first on 2026-10-02: it is the narrower scope, but in UT's tenant it needs admin approval that has not been granted, so sign-in stalled.
- **Snapshotting every plan from `/me/planner/plans`.** Unbounded, and pulls in boards unrelated to any LifeOS thread.
- **Implicit cross-service refresh.** A request for one domain does not select every other enabled service; refresh composition belongs to the calling workspace.

## Experimental Move Extension
The experimental extension provides dry-run-first `move-task --task ID --plan ID --bucket ID` using the [documented Graph beta task update](https://learn.microsoft.com/en-us/graph/api/plannertask-update?view=graph-rest-beta). The current implementation limits moves to two allowlisted plans in the same Microsoft 365 group, validates bucket membership, refuses active labels, recurrence and externally sourced tasks, and uses one ETag-guarded PATCH. It audits the attempt and verifies the destination and supported preserved fields. It never clones or deletes tasks and never retries an ambiguous write. Goals, custom columns and linked meeting notes remain outside verification. Offline tests are available. Same-group moves were validated live on 2026-10-11 with readback confirming task IDs, descriptions, assignments, dates, progress, priority and destinations. Nonempty checklist/reference and conversation preservation remains unverified live.
